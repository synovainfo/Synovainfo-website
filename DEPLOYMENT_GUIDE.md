# Synova Website Deployment & Server Guide

This document contains critical instructions, troubleshooting steps, and lessons learned for deploying the Synova website on a cPanel/GoDaddy environment. 

This project was historically migrated from a Prisma/Node backend to standard Laravel 12. As a result, there are specific quirks regarding database schema formatting (camelCase vs snake_case) that have been permanently resolved but must be kept in mind for future updates.

## 1. Deployment Workflow (cPanel Git Version Control)

When you make changes to the code locally and push them to GitHub, the server **does not** update automatically. You must manually trigger the pull from cPanel.

### Step 1: Pull the Code
1. Log into your GoDaddy Hosting Dashboard.
2. Click **cPanel Admin**.
3. Scroll to the "Files" section and click **Git Version Control**.
4. Click **Manage** next to the `synovainfo/Synovainfo-website` repository.
5. Go to the **Pull or Deploy** tab.
6. Click **Update from Remote**. 
7. Wait until you see the green success banner. **Check the HEAD Commit message** above the button to ensure it matches your latest commit on GitHub.

### Step 2: Clear Caches (If needed)
If you made changes to configurations (`.env`, `config/`), run this in your SSH terminal:
```bash
php artisan optimize:clear
```

### Step 3: Run Database Migrations
If you created new database migrations, run them in the SSH terminal:
```bash
php artisan migrate --force
```
*(Never run `migrate:fresh` on a live production server, as it wipes all data! Only use `migrate:fresh` for initial setup/testing).*

## 2. Domain & Document Root Configuration

By default, cPanel assigns addon domains to empty folders (e.g., `/home/username/synovainfo.com`). For a Laravel application, the entry point is `/public_html/index.php`. 

To ensure the domain points to the correct folder:
1. Open **cPanel Admin**.
2. Click **Domains**.
3. Find your domain (e.g., `synovainfo.com`) and click **Manage**.
4. Ensure the **New Document Root** is exactly `/public_html`.
5. Click **Update**.

*(Note: If the GoDaddy dashboard throws a "Something went wrong" modal when trying to change the Primary Domain, ignore the GoDaddy interface and use the exact cPanel method above).*

## 3. The `camelCase` vs `snake_case` Database Architecture

**CRITICAL CONTEXT:** 
The original database schema was generated by Prisma, which enforced `camelCase` table columns (e.g., `createdAt`, `authorId`, `featuredImage`). When the project transitioned to Laravel 12, all new migrations were built using standard Laravel `snake_case` conventions.

We executed a massive standardization patch to convert the entire database and codebase strictly to `snake_case`. 

### What to Remember for Future Development:
1. **Never use `camelCase` for database columns.** If you create a new migration, use standard Laravel formatting: `$table->string('author_id')`, NOT `$table->string('authorId')`.
2. **Relationships:** The `HasCamelCaseColumns` trait is still active on legacy models to translate any rogue hardcoded `camelCase` foreign keys in relationships. However, for new relationships, write them natively in `snake_case`: `$this->belongsTo(User::class, 'author_id')`.
3. **Controllers:** All controllers have been converted to query `snake_case` explicitly (e.g., `orderBy('created_at', 'desc')`). Never write `orderBy('createdAt')` in a new controller, as the database column no longer exists in that format.
4. **Seeders:** Ensure all arrays in Seeders use `snake_case` keys (e.g., `['tag_id' => $id]`) to map correctly to the database.

## 4. SSH Access & PHP Version
- The server runs **PHP 8.3**.
- Always ensure you are running `php artisan` commands from the root directory (`~/public_html` or `~/laravel_app` depending on your cPanel structure).

## 5. Storage Symlink
If images or uploaded files are returning 404 errors, ensure the storage symlink is active:
```bash
php artisan storage:link
```
